# Образцовая БД больницы / Hospital Reference

Локальная реляционная модель больничной сети для PostgreSQL 18 и PostGIS 3.6. Создана в отдельной базе **hospital_reference**. Существующие базы не изменяются.

Модель охватывает путь от регистрации пациента и записи на приём до эпизода лечения, диагностики, госпитализации, выдачи лекарств, расчётов и контроля качества. В ней разделены идентичность пациента, медицинские факты, административные события и финансовые документы.

Весь набор данных искусственный: `DEMO-*` MRN, `SYNTH-*` идентификаторы, имена «Пациент / Синтетический», адреса `example.invalid`, учебные вещества и препараты. Внешние документы и DICOM представлены **метаданными**, а не настоящими файлами. Клинические коды `urn:demo:*` не подменяют полные справочники МКБ, LOINC, SNOMED CT или национальные реестры.

## Открыть

В pgAdmin добавьте сервер: host `localhost`, port `5432`, maintenance database `hospital_reference`, пользователь вашего локального PostgreSQL `postgres`. Пароль остаётся тем, который установлен при предыдущей настройке. Он не хранится в проекте.

Откройте **Databases → hospital_reference → Schemas**. Для примеров SQL используйте файл `examples.sql`. Для обзора модели откройте `report.html` и `DATA_MODEL.md`. Фактические размеры и число строк находятся в `catalog.json`; результаты проверок — в `validation_results.csv` и `VERIFICATION.md`.

## Масштаб генератора

120 002 пациента, 600 сотрудников, 30 отделений, 480 коек, 330 000 эпизодов, 1 320 000 измерений, 360 000 лабораторных результатов, 120 000 записей на приём, 90 000 лекарственных назначений, 180 000 счетов и 150 000 платежей. Суммарное число строк и размер вычисляются по установленной базе, а не берутся из этой декларации. Генератор не использует случайное смешивание медицинских рекомендаций: это модель данных и процессов.

## Развёртывание с нуля

1. На новом PostgreSQL установите PostGIS и проверьте наличие `btree_gist`, `pgcrypto`, `pg_trgm`.
2. Задайте `PGPASSWORD` **только для текущего процесса** администратора; либо используйте безопасный локальный password file PostgreSQL.
3. Выполните `deploy.ps1`, затем `07_hardening.sql` и `09_authorized_workflows.sql` через `psql -v ON_ERROR_STOP=1`.
4. Запустите `08_validate.sql` из папки проекта. Все изменяющие тесты работают в транзакции и заканчиваются `ROLLBACK`.
5. Выполните `ANALYZE` после массовой загрузки. Обновите материализованные представления после новых данных.

Развёртывание откажется перезаписывать существующую `hospital_reference` или присваивать существующие роли. При ошибке миграция остаётся доступной для диагностики. SQL-файлы разделены по этапам; номер успешного этапа записывается в `ops.schema_migration`. Скрипт не удаляет частично созданную базу автоматически. Численность, распределения и связи генератора воспроизводимы; UUID и служебные отметки времени формируются заново при каждом развёртывании.

## Права

Роли `hospital_owner`, `hospital_clinician`, `hospital_registrar`, `hospital_billing`, `hospital_analyst`, `hospital_auditor` не могут входить самостоятельно. Три `hospital_demo_*` principal также **NOLOGIN**: они предназначены для воспроизводимых проверок из административной сессии, а не являются общедоступными аккаунтами с известным паролем.

Врач видит только назначенных ему пациентов и их медицинские записи. Регистратор получает демографию и запись на приём без клинических текстов. Финансовая роль получает счета и ограниченное представление идентичности. Аналитик получает агрегаты. Аудитор читает журнал, но не изменяет его. У демонстрационных пользователей доступ открыт к первым 100 пациентам; истёкший break-glass к пациенту 101 не даёт доступа.

Идентичность определяется `session_user`, а не изменяемыми `app.user_id`/`app.patient_id`. Нельзя использовать один общий PostgreSQL-login для всех пользователей и ожидать, что эти политики различат людей: для реального приложения нужен спроектированный доверенный шлюз идентичности или отдельные principals. Администратор `postgres` имеет полный доступ и обходит RLS — это административная учётная запись, а не учётная запись приложения.

## Эксплуатация

- `ehr.observation` разделена помесячно на 2024–2027 годы. Создавайте следующие партиции заранее; строки вне подготовленного горизонта намеренно отвергаются.
- Временные интервалы занятости — `[начало, конец)`. Это допускает стык визитов без ложного пересечения. Моменты времени хранятся как `timestamptz`; отображение настроено на `Asia/Qyzylorda`.
- Для обновления с защитой от потери изменений используйте `WHERE id=:id AND row_version=:expected_version` и проверяйте число изменённых строк. Примеры есть в `examples.sql`.
- Складские изменения проводятся добавлением движений; баланс меняется под блокировкой строки. Выдача препарата и складское списание — одна транзакция.
- Распределение денег блокирует сначала платёж, затем счёт. Приложение должно соблюдать этот порядок и повторять транзакции при `40P01`/`40001`. Тест конкурентного списания проверяет отсутствие отрицательного остатка.
- Аудит DML включён **после** синтетической загрузки; она обозначена `BASELINE`, а не выдаётся за подлинную историю действий. Последующие изменения фиксируются автоматически. Чтение надо регистрировать через `audit.record_patient_access()` на уровне приложения; обычный `SELECT` сам по себе не вызывает триггер.
- `outbox` не отправляет сообщения самостоятельно: необходим worker. Уникальные idempotency keys и inbox предотвращают повторы на уровне хранения; внешний транспорт должен реализовать retries, DLQ и мониторинг.
- `REFRESH MATERIALIZED VIEW CONCURRENTLY analytics.daily_activity` и аналогичный запрос для `monthly_revenue` обновляют отчёты. Время актуальности должно контролировать приложение/планировщик.

## Резервная копия

`hospital_reference.backup` — полный архив `pg_dump` в custom format. `schema.sql` — читаемая выгрузка схемы. `roles.sql` содержит только роли и членство, без паролей.

Восстанавливайте архив в **новую пустую** базу с установленными расширениями и подготовленными ролями. `restore.ps1 -NewDatabase hospital_reference_copy` создаёт такую базу и восстанавливает также настройки CONNECT и часового пояса, которые нельзя считать автоматически перенесёнными обычным архивом без CREATE DATABASE. Скрипт использует `--enable-row-security`: это необходимо при восстановлении материализованных агрегатов с владельцем без BYPASSRLS и источниками под FORCE RLS. Явная политика владельца разрешает их штатное заполнение; политики прикладных ролей сохраняются. Не используйте `--clean` против работающей базы. Проверка восстановления выполнена в отдельной временной базе; фактический результат приведён в `VERIFICATION.md`. Для реального сервиса нужны регулярные внешние бэкапы, PITR, контроль RPO/RTO и периодические учения по восстановлению.

## Границы готовности

Это большой проверяемый **референсный стенд**, а не сертифицированная медицинская информационная система. В комплект не входят интерфейс медицинского работника, сервер FHIR, подключение национальных реестров/ОСМС, клиническая валидация справочников, квалифицированная ЭЦП, эквайринг и реальные внешние интеграции. Хэш подписанного текста не является юридически значимой ЭЦП. Для реального внедрения отдельно проектируют локальные регламенты, согласия, сроки хранения, ключи шифрования, защищённый транспорт, отказоустойчивость, лечебные workflows и нагрузочный профиль.
